# ProjectFlow Assessment Notes

## Architecture Understanding

### How is the application structured, and what are the major modules?
The application is a TypeScript monorepo managed with `pnpm` workspaces and Turborepo. It consists of:
1. **API (`apps/api`)**: A NestJS backend connected to MongoDB via Mongoose. Major modules include Authentication, Users, Organizations, Projects, Tasks, and Comments, alongside relationship management modules like OrganizationMembers and ProjectMembers.
2. **Web (`apps/web`)**: A Next.js (App Router) React frontend styled with Tailwind CSS and Radix UI. It separates UI primitives (`components/ui`) from business domains (`features/*`).
3. **Shared (`packages/shared`)**: Contains TypeScript types, interfaces, enums, and constants used by both applications to maintain a single source of truth for the domain and API contract.

### Where does business logic live?
In the backend, business logic is centralized within the **Service** layer of each module (e.g., `TasksService`). Controllers are thin and only map HTTP requests to service calls. Input validation occurs at the boundary using DTOs with class-validator. 

### How does the frontend talk to the backend, and how is server state handled?
The frontend communicates with the backend via a centralized `api-client.ts` fetch wrapper, which automatically injects the JWT bearer token from local storage.
Server state is managed entirely by **TanStack Query (React Query)**. Query keys are centralized in `lib/query-keys.ts` to ensure consistent cache invalidation when mutations succeed.

### How are authentication and authorization implemented?
- **Authentication**: Stateful via JWT bearer tokens. A global `JwtAuthGuard` secures the API, requiring routes to explicitly opt-out with a `@Public()` decorator. Passwords are hashed with bcrypt.
- **Authorization**: Centralized in the `ProjectAccessService` which validates two levels of access:
  1. *Organization Role*: Elevated roles (`OWNER`, `ADMIN`) bypass project-level checks.
  2. *Project Role*: Explicit rows in the `project_members` collection grant `PROJECT_MANAGER` or `MEMBER` permissions.
  The service provides `assertCanView` for read operations and `assertCanManage` for write/admin operations.

### How are the main entities related?
The entities use normalized relationships rather than embedded documents to allow efficient querying and indexing:
- `Organization` 1:N `Project`
- `Project` 1:N `Task`
- `Task` 1:N `Comment`
- Membership is tracked through bridging collections (`OrganizationMember` and `ProjectMember`) connecting a `User` to an `Organization` or `Project`, respectively, along with an assigned `role`.

## Identified Risks & Weaknesses

### 1. Authorization Bypass on Task Status Updates
**What I noticed:** The `PATCH /tasks/:taskId/status` endpoint and the underlying `updateStatus` method in `TasksService` lack any authorization checks. It doesn't take a `userId` parameter or verify if the user belongs to the project.
**Why it could be a problem:** Any authenticated user can modify the status of any task across the entire system if they guess or know the Task ID, breaking data integrity and security.
**Fix it now or later:** **Now**. This is a severe security vulnerability that violates tenant isolation. I will address this as part of the "Production Bug Investigation".

### 2. Race Condition in Task Numbering
**What I noticed:** Task numbers are generated by calling `taskModel.countDocuments()` and adding 1. 
**Why it could be a problem:** In a concurrent environment, if two users create a task in the same project simultaneously, both requests read the same document count and generate identical task numbers (e.g., two tasks named `ENG-6`). This breaks the uniqueness expectation of the human-readable identifier.
**Fix it now or later:** **Now**. This is a core requirement of the assessment to ensure concurrent task creation is safe. I will replace it with an atomic `$inc` operation.

### 3. Lack of Token Revocation / Refresh Flow
**What I noticed:** Authentication relies on long-lived (7-day) JWT access tokens without a refresh token mechanism or a server-side revocation list.
**Why it could be a problem:** If a token is compromised (e.g., XSS attack reading local storage), the attacker retains access for up to 7 days. Additionally, users changing passwords or being removed from organizations will retain their access until the token expires naturally.
**Fix it now or later:** **Later**. While a serious security posture weakness, introducing a refresh flow with HTTP-only cookies and a Redis-backed blocklist is a significant architectural change outside the immediate 4-hour scope of this assessment. 

### 4. Missing API Rate Limiting
**What I noticed:** There is no rate limiting (e.g., `@nestjs/throttler`) configured on the API.
**Why it could be a problem:** The `/auth/login` endpoint is vulnerable to brute-force credential stuffing. Other endpoints are vulnerable to DoS attacks or excessive scraping.
**Fix it now or later:** **Later**. This is easily solved by adding the NestJS throttler module, but given the time constraints, fixing the data integrity bugs takes priority.

## Code Review

### 1. `apps/api/src/comments/comments.service.ts`
**Review:**
- **Security**: The `findByTask` and `create` methods correctly enforce authorization by asserting the user can view the project via `projectAccessService.assertCanView(task.projectId, userId)`.
- **Database/Performance**: The `toEntries` method aggregates `authorId`s from all comments and passes them to `usersService.findManyByIds()`. However, it does not deduplicate the `authorId`s first.
  ```typescript
  const authors = await this.usersService.findManyByIds(
    comments.map((comment) => comment.authorId),
  );
  ```
  If a single user leaves 50 comments on a task, `findManyByIds` is called with an array of 50 identical ObjectIds, causing the database to do unnecessary work and transferring more data than needed.
**Recommendation**: Deduplicate the `authorId`s using a `Set` before querying `usersService.findManyByIds`.
  ```typescript
  const authorIds = Array.from(new Set(comments.map((c) => c.authorId.toString()))).map(id => new Types.ObjectId(id));
  const authors = await this.usersService.findManyByIds(authorIds);
  ```

## Scaling Answer

**Question:** In production, an organization could have millions of tasks. What potential performance issues could occur with this API and data model, and how would you address them?

### Potential Performance Issues
1. **Unbounded Queries and Missing Indexes**: 
   The current queries, especially in the tasks and comments services, may not scale efficiently without covering indexes. If the `projectId` and `status` query is performed on millions of tasks, MongoDB will perform collection scans if adequate compound indexes don't exist, leading to heavy CPU/RAM utilization and slow response times.
2. **N+1 Query Problems in Data Serialization**: 
   The API resolves foreign keys (e.g., `createdBy` and `assigneeId` for Tasks, `authorId` for Comments) by fetching referenced users in code (`usersService.findManyByIds`). As the page size grows or the task volume increases, resolving user data out-of-band across microservices or distinct collections can become a bottleneck.
3. **Large Payloads**: 
   Returning 100 tasks at once for a Kanban board (as configured in the frontend) with fully populated user data and task details can create massive JSON payloads, consuming bandwidth and slowing down serialization and deserialization.

### Proposed Solutions
1. **Compound Indexing**:
   - Add a compound index on `tasks` for `{ projectId: 1, status: 1, createdAt: -1 }` to support efficient filtering and sorting of tasks by status within a project.
   - For user lookup, ensure the `_id` field in the `users` collection is efficiently indexed and utilize `$in` queries (already doing this, but ensure proper batching).
2. **Denormalization**:
   - Cache essential user details (e.g., `name`, `avatarUrl`) directly within the `Task` and `Comment` documents. This avoids the N+1 problem completely at read-time and only requires an asynchronous fan-out update when a user changes their profile.
3. **Data Fetching and Pagination**:
   - Implement cursor-based pagination (using the `_id` or `createdAt` fields) rather than offset-based pagination (`skip` and `limit`). Offset-based pagination becomes progressively slower as the offset grows, as MongoDB must scan and skip the first N documents.
   - For Kanban boards, instead of fetching 100 tasks per column, implement virtualized scrolling in the UI and fetch tasks lazily as the user scrolls down a specific column, ensuring low initial load times.
4. **Caching Layer**:
   - Introduce a caching layer like Redis for frequently accessed project data and tasks, especially for the initial board load which reads heavy. Cache invalidation can be triggered on task creation or updates.
